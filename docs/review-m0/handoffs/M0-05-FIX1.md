## 根因

### B-01：逻辑改名复用了材料级陈旧证据

`DeterministicReviewEngine` 把同扩展名逻辑改名视为仅影响 `FILE_NAME_NONCOMPLIANT`。增量合并因而保留 changed material 旧的 `CANNOT_CONFIRM` finding；该 finding 的 evidence 是材料快照的一部分，仍携带旧 `submissionFileName`。

### B-02：扩展名改变没有扩大类型影响集合

`IncrementalReviewValidator` 只根据材料来源字段是否变化决定 `nameOnly`，没有区分“同扩展名改名”和“扩展名与正式类型兼容性发生变化”。防御性 manifest 中 `before.pdf -> after.docx` 因而沿用最小命名路径，遗漏完整审查会产生的 `CANNOT_CONFIRM/TYPE_MISMATCH`。

### B-03：幂等摘要错误包含服务器可变快照

`FormalReviewSubmissionService` 以完整执行 envelope 的摘要作为 M0-02 幂等请求摘要。envelope 包含每次提交时捕获的服务器 manifest；同一 HTTP 请求和 key 在逻辑名变化后会先重新捕获快照，再被误判为不同请求。

## 修复算法

### 增量影响集合

- `IncrementalPlan` 显式携带 `recomputeCompleteness` 分类。
- 合法同扩展名 name-only 改名仍走最小路径：复用与 changed material 无关的 findings；删除 changed material 的旧材料级 findings；按当前 manifest 重建其 `CANNOT_CONFIRM` 和命名 findings。未受影响 finding 保持复用，不是无条件完整重审。
- 当逻辑名变化使扩展名与 `formalFileType` 的兼容性发生切换时，plan 扩大为重新计算全局 completeness/type/CANNOT_CONFIRM，再只重算 changed material 的命名 finding。这样增量与完整审查对最终输入产生相同 findings、evidence、计数与 assessment，同时保持整份 `MISSING` 抑制。
- 没有放宽 M0-04 的正常写路径；这里只防御迁移、适配器或历史 manifest。

### 幂等与首次执行 envelope 分离

- 客户端规范请求摘要只包含 owner、case、HTTP method、canonical endpoint path 与 `FormalReviewRequest` 的规范 HTTP payload，用于 M0-02 claim/replay。
- Job 的 `request_json` 与 Job `requestDigest` 仍保存首次不可变执行 envelope 及其摘要；`inputFingerprint` 仍来自首次 manifest。
- 在捕获服务器快照前检查已完成的同 scope 幂等记录。相同 owner/case/endpoint/body/key 直接返回首次 Job，不重新捕获 manifest；同 key 不同 body 仍稳定冲突。
- 不同 key 会捕获当前 manifest，生成对应的新 fingerprint/Job；owner、case、endpoint 作用域和资源所有权校验没有弱化。
- 没有修改 M0-02 Store 语义或 SPI，也没有从 Job envelope 删除服务器状态。
