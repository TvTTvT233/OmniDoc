## 2. 已实现能力

### 2.1 正式审查门与不可变输入

- `CurrentReviewInputProvider` 只通过 M0-02/03/04 owner-aware 边界读取案例、当前正式清单、材料、已确认分配、逻辑 `submissionFileName` 和上传确认；异主案例表现为不存在。
- `FormalChecklist` 严格校验不可变 snapshot JSON/digest，只接受未 supersede 的 `CONFIRMED` 快照，拒绝未决条件项；官方 quoted text 不进入审查元数据或证据。
- 上传确认必须精确绑定 owner、case、当前 checklist snapshot 和当前 `materialSetRevision`。旧确认或缺确认在同步提交门拒绝，不创建 Job、报告或发现。
- `ReviewInputManifest` 保存无正文、无 object key 的不可变输入事实；`ReviewInputFingerprint` 包含契约、引擎、案例、依据、清单、材料、分配、逻辑名和上传确认，列表按 Unicode code point 稳定排序。
- 提交阶段不读取文件字节；执行阶段使用 M0-04 `requireReviewReadyOwned`。文件/数据库/未知系统错误终结 Job，不发布业务发现或报告。

### 2.2 确定性齐全性与命名

- `DeterministicReviewEngine` 是纯本地确定性引擎，不构造或调用模型、远程授权、Agent、Memory/MCP/Qdrant。
- 对每个 `APPLIES` 项按 `minimumCount`、当前 `USER_CONFIRMED` 分配、去重 materialId 和 `AVAILABLE` 状态计数。
- 当前提交存在任一冻结 `CANNOT_CONFIRM` 时，输出对应原因并抑制整份报告全部 `MISSING`；其他可靠材料的命名检查仍执行。
- 实现 `EXACT`、`REGEX`、`NONE`、显式大小写、NFC 完整匹配、扩展名不区分大小写和全局安全逻辑名；只使用 `submissionFileName`。
- 类型不一致输出 `CANNOT_CONFIRM/TYPE_MISMATCH`，不输出普通命名发现。已发布坏正则、编译失败、超时或内部失败按系统错误处理。
- 错别字、漏填、资格、签章日期、跨材料一致性、证明支持和写作质量不在引擎输入或输出语义中。

### 2.3 证据、报告、新鲜度与忽略

- `ReviewEvidenceFactory` 生成规范化双侧证据。`MISSING` 规则侧包含 checklist/item/rule revision、minimumCount 和官方 locator；材料集合侧包含上传确认、当前材料/来源/分配/计数摘要。
- 命名发现包含规则 ID、规则修订、期望模式或全局安全原因，以及对应材料 snapshot；不复制材料正文、官方全文、预览、原始文件名或 object key。
- `ReviewReportAssembler` 生成不可变完整报告；只有三类发现均为零时才生成 `M0_READY`。新报告发布时 ignoredCount 必为零且 freshness 为 `CURRENT`。
- M0-02 `ReviewReportStore.publishOwned` 提供 `(caseId,inputFingerprint)` 唯一、报告/发现/证据/Job 结果原子发布、旧当前报告 `OUTDATED` 和崩溃/重试幂等。
- `FindingDecisionService` 只追加不可变 `IGNORE` 事件；不删除发现/证据、不修改历史报告、不提供撤销，重复同一决定返回原事件。有效投影折叠 `ignoredCount`，存在忽略时始终 `M0_NOT_READY`。
- `EngineFreshnessService` 使用 M0-02 `RevisionKind.ENGINE_VERSION` 使不同引擎版本的当前报告不可逆 `OUTDATED`；M0-02 回归覆盖全部冻结 revision 触发器。

### 2.4 完整与单材料增量重审

- `FormalReviewSubmissionService` 支持 `FULL` 和 `INCREMENTAL`，在 owner/case 行锁和同一事务中完成同步门、增量基准校验和幂等 Job 提交。
- Job request 保存完整不可变 manifest，因此基准校验不依赖已变化的材料行，也无需扩展 M0-02 SPI/DDL。
- 增量请求必须声明同案例 `baseReportId` 和精确 `changedMaterialIds`；依据、清单、契约、引擎、未声明变化、无变化、旧上传确认或 revision 不匹配统一稳定失败为 `REVIEW_M0_INCREMENTAL_BASE_MISMATCH`，不静默回退。
- 单文件逻辑改名只重算该材料的命名影响；材料、来源、诊断或分配变化重算全局齐全性/CANNOT_CONFIRM 影响并只重算变化材料的命名。
- 对同一最终输入，增量与完整重审复用相同规范化 `FindingDraft`/`EvidenceDraft`，报告计数和 assessment 等价；只允许 ID 和时间不同。
- `FormalReviewJobHandler` 与 `IncrementalReviewJobHandler` 分别实现 M0-02 `FORMAL_REVIEW`/`INCREMENTAL_REVIEW` SPI 槽，registry 测试证明两槽无冲突。

## 6. 契约冲突与 M0-06 接线入口

未发现必须修改 M0-02 model/store/job/idempotency/db 的 SPI 缺口，也未复制上游领域类型。不可变 Job `request_json` 足以保存 M0-05 manifest 并做严格增量基准校验。

M0-06 可依赖并负责组合/注册以下入口：

1. 提交门：`CurrentReviewInputProvider` + `FormalReviewSubmissionService.submitOwned(...)`。
2. Job：用同一个 `ReviewM0ReviewJobExecutor` 构造 `FormalReviewJobHandler`、`IncrementalReviewJobHandler`，把两者注册为 M0-02 `ReviewM0JobHandler` beans；M0-05 未越权新增 Spring/API 配置。
3. 引擎：`DeterministicReviewEngine.ENGINE_VERSION`、`BoundedRegexMatcher`、`ReviewEvidenceFactory`。
4. 报告读取：`JdbcReviewReportReader` / `ReviewReportReader.requireOwned(...)`。
5. 忽略与有效投影：`FindingDecisionService.ignoreOwned(...)`、`getEffectiveOwned(...)`。
6. 引擎升级过期：在接受新版本审查前调用 `EngineFreshnessService.invalidateDifferentEngineOwned(...)`，再捕获新的当前输入；不能在已经捕获 manifest 后推进 Case version。
7. 发布路径：`ReviewReportAssembler` + M0-02 `ReviewReportStore.publishOwned(...)` 已由 handler 使用；API 不应自行写报告、发现、证据或决定表。

Integrated 保持 `PENDING_INTEGRATION` 是预期状态：M0-06 仍需提供 HTTP/auth 映射、Spring 组合和最终 production adapter；真实 owner-aware file-service、MySQL 与外部服务验证也尚未完成。
