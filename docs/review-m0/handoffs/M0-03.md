## 2. 已实现能力

### 2.1 官方依据与候选清单

- 官方依据只能通过显式 `attachOwned` 及角色进入依据集；普通材料没有自动升级路径。
- 附加、重新分类和停用使用 M0-02 的 Case owner 隔离及 basis 修订/`STALE_BASIS` 入口；解析成功和 `CANNOT_CONFIRM` 状态带版本 CAS。
- 本地抽取通过 `OfficialBasisContentProvider` 与 `LocalChecklistCandidateExtractor` 两个显式适配口完成；测试使用确定性适配器。
- 官方提取项必须提供非空 `basisId`、可核对 `sourceLocator` 和有界非空 `quotedText`，否则整个候选结果拒绝且不落草稿。
- 官方提取、用户新增和用户改写分别保持 `origin/authorship`；官方项改写保留原 `sourceRefs` 并新增不可变 requirement revision；停用只新增历史修订且不进入新快照。
- 候选始终保存为 `CANDIDATE_DRAFT`；正式审查读取入口只接受 Case 当前 `CONFIRMED` 快照。
- 发布要求当前 basis、全部附着依据 `READY`、当前草稿 revision、启用 ID 精确逐项确认、无 `NEEDS_USER_DECISION`，并校验 `EXACT/REGEX/NONE`、显式 `caseSensitive` 和保守正则安全边界。
- 正式 `ChecklistSnapshot` 使用 M0-02 的 `publishChecklistSnapshotOwned` 原子发布且内容不可变；依据修订后旧快照变 `STALE_BASIS` 并不能用于审查。

### 2.2 隐私脱敏与远程授权

- `LOCAL_ONLY` 分支不会调用 `RemoteCandidateClientFactory.create()`，也不会构造或调用远程 client。
- 脱敏预览持久化 `operation`、basis revision、preview version 和确认载荷 digest；发往远端的规范字节只含按 `segmentId` 排序且 `included=true` 的脱敏文字，不含 `basisId/sourceLocator`。
- 预览编辑保留来源身份并产生新 version/digest；即使文字后来改回同一 digest，旧未消费确认也因确认代次不是当前确认而保持失效。
- `RemoteConsentVerifier` 在产生副作用前核验 owner、case、远程模式、Job 请求中的 consent/revision、operation、Job 状态、租约 owner/期限、当前 preview、digest 和消费状态。
- `beginSendIntent` 复用 M0-02 原子消费 consent 与 `SEND_INTENT`；两个逻辑 Job 竞争同一 consent 只有一个成功。
- 实际发送字节在 client 构造前再次计算 digest；只有与确认 digest 完全相等才调用显式注入 client。
- `SEND_INTENT` 恢复时不得自动重发：无可查询结果即标为 `OUTCOME_UNKNOWN`；已持久化 `RESPONSE_RECORDED` 时只走本地结果恢复，不再返回发送授权。
- 远程失败只使 Job `FAILED`；响应只可在 Job 结果发布事务内创建 `CANDIDATE_DRAFT`，不创建快照、报告或 finding。
- 没有 Spring 自动装配、默认供应商、默认模型、Prompt、公共 YAML 或凭据入口；M0-06 必须显式注入外部实现。
- 新代码没有日志器；Job 请求、错误、checkpoint、remote-call 审计元数据只保存 ID、规范请求、摘要和安全状态，不保存依据全文、预览正文、载荷、响应或 Prompt。预览正文和候选正文只存在于其本地业务记录中。

## 6. 契约边界与兼容建议

没有阻塞 M0-03 的 M0-02 SPI 缺口，也没有修改 M0-02 文件。以下两点留给集成阶段明确处理：

1. 冻结 M0-02 `FileNameRule` 在非法 REGEX 时把 `PatternSyntaxException` 保留为 cause；其 cause 文本可能回显用户规则。M0-03 的 Job/存储异常均已去除敏感 cause，但若 M0-06 直接把模型异常树序列化到 API/日志，会违反“用户编辑正文不进入异常”的边界。最小兼容修正建议是在 M0-02 后续专门修订中去掉该 cause，或由 M0-06 只输出顶层冻结错误码/安全消息，绝不序列化 cause。
2. M0-02 的 `publishChecklistSnapshotOwned` 把 Case `checklistRevision` 作为最后一次正式发布 revision；M0-03 的每次候选编辑修订保存在 `review_m0_checklist_revision.revision_number`，发布时再同步 Case。若后续要求 Case 字段实时表示未发布草稿 revision，需要先扩展 M0-02 的 CAS/发布约定，不能由 M0-03 单方面更新而破坏现有发布前置条件。
