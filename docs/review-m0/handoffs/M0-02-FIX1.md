## 2. 根因与修复

### 2.1 跨 owner Case 创建 Job

根因：`ReviewM0JobSubmissionService` 虽然要求 scope owner 与 Job owner 相同，但 `JdbcReviewM0JobStore.create` 直接插入 Job，未在数据库写入条件中验证 Case 同 owner 存在。攻击者可给异主 Case 创建 Job，并留下已完成的幂等记录。

修复：Job 创建改为 `INSERT ... SELECT`，只从 `(case_id, user_id)` 同时匹配的 Case 原子创建。匹配失败统一抛出 `REVIEW_M0_CASE_NOT_FOUND`，且与幂等 claim 位于同一事务，失败时不留下 Job 或幂等记录。并发异主提交同样全部失败且无可探测状态。

主要回归：

- `crossOwnerCaseSubmissionIsNotFoundAndLeavesNoJobOrIdempotencySideEffect`
- `concurrentCrossOwnerSubmissionsAllFailWithoutCreatingProbeableState`

### 2.2 跨 Case 报告发布

根因：报告发布锁定了 Job，但没有完整核验 Job、报告、Case owner、输入指纹、上传确认和成功重放结果的共同绑定；发布自身的事务边界也依赖内部 Store 调用，无法保证报告、Job 结果和 Case 当前报告指针整体回滚。

修复：`publishOwned` 增加覆盖完整发布过程的外层事务；在锁定 Job 后原子核验：

- `job.case_id == report.case_id`；
- Job 对应 Case 与请求 owner 一致；
- Job 类型为 `REVIEW`；
- `job.input_fingerprint == report.input_fingerprint`；
- 首次发布时租约 owner、租约期限、状态和最终 Job version CAS 有效；
- upload confirmation 与同一 owner/Case/快照/材料修订绑定；
- Job 已成功时，仅允许复用该 Job 已实际绑定、且所有冻结修订和输入指纹完全一致的原报告。

任一核验失败时，报告、finding/evidence、Job 结果、Case 当前报告指针和幂等记录全部保持不变。

主要回归：

- `crossCaseAndOwnerPublicationRollsBackReportJobPointerAndIdempotencyState`
- `reportInputFingerprintMustEqualTheLeasedJobAndFailureHasNoPublicationSideEffect`
- `succeededJobCannotBeIdempotentlyReusedToProbeAnotherCaseReport`

### 2.3 RemoteConsent 绑定不足

根因：原 SEND_INTENT 路径主要按 consent id 与 digest 消费授权，没有把 Case/owner、operation、当前 basis revision、预览状态和目标逻辑 Job 一并锁定核验；读取接口也仅按 Job 查询，形成跨 owner/Case 探测面。

修复：

- SEND_INTENT 先锁定并核验目标 `CHECKLIST_EXTRACTION` Job 的租约、Job Case、Case owner 和当前 basis revision；
- 加锁读取 consent 与 preview，严格核验 owner、caseId、operation、consent/preview revision、preview `CONFIRMED` 状态、consent/preview/request 三方 payload digest；
- 首次消费使用包含全部绑定字段与 `consumed_at IS NULL` 的 CAS，然后在同一事务写入唯一 SEND_INTENT；
- 已消费授权只有在相同逻辑 Job 已存在完全匹配的 remote call 时才作为幂等恢复返回；已消费但无匹配调用、跨 Job 重复消费均拒绝；
- 公共读取改为 `findOwned(ownerId, caseId, jobId)`，并通过 Job、Case、consent、preview 的完整连接约束 owner/Case/逻辑 Job；无 owner 的查询仅保留为 Store 私有事务内部实现。

竞争消费仅一个逻辑 Job 成功；失败事务不改变 consent 或 remote call 状态。真实远程发送仍不在本任务范围。

主要新增回归：

- `crossOwnerAndCaseConsentIsHiddenAndLeavesConsentAndCallStateUntouched`
- `mismatchedConsentOwnerOnTheSameCaseCannotAuthorizeSendIntent`
- `oldBasisRevisionAndInvalidatedPreviewCannotAuthorizeSendIntent`
- `operationMismatchCannotAuthorizeSendIntentEvenWithTheSameDigest`
- `consumedConsentWithoutItsMatchingRemoteCallCannotBeConsumedAgain`
- `concurrentConsentConsumptionAllowsExactlyOneLogicalJob`

已有 `confirmedPayloadDigestMustMatchActualSendBytes` 保持通过，继续覆盖 payload digest 不匹配；已有同逻辑 Job 幂等恢复测试保持通过。

### 2.4 ZIP 容器冒充材料

根因：`SubmissionMaterial` 允许 `FormalFileType.ZIP` 作为 `TOP_LEVEL_FILE` 材料，V001 材料类型约束也包含 ZIP，混淆了“支持的顶层输入容器”和“可满足清单的材料单元”。

修复：

- `FormalFileType.ZIP` 与 `SubmissionSource` 的 ZIP 支持契约保持不变；没有新增同义枚举；
- `SubmissionMaterial` 只接受五类冻结叶子格式，ZIP 无论以 `TOP_LEVEL_FILE` 或 `ZIP_ENTRY` 形态都不能成为材料；
- V001 的 `review_m0_material` 类型约束同步收紧为五类叶子格式，而 `review_m0_submission_source` 继续允许 ZIP；
- 未实现 ZIP 展开、叶子生成或嵌套 ZIP 处理，这些仍属于 M0-04。

主要回归：

- `zipRemainsAFormalInputContainerButCannotBecomeAMaterialUnit`
- `zipSourceIsSupportedButDatabaseRejectsTheContainerAsAMaterialUnit`

### 2.5 strict validate 漏检 V002 外键

根因：严格 schema 校验只覆盖表、列、版本与部分索引，没有检查 V002 四个循环外键，因而缺失关键外键仍会启动成功。

修复：使用 JDBC metadata 按引用结构而非约束名称，核验以下四个 V002 外键的源表/列、目标表/列、单列 key sequence，以及限制性的删除/更新规则（`NO ACTION`/`RESTRICT`）：

- `review_m0_case.current_checklist_snapshot_id -> review_m0_checklist_snapshot.checklist_snapshot_id`
- `review_m0_case.current_report_id -> review_m0_report.report_id`
- `review_m0_checklist_revision.extraction_job_id -> review_m0_job.job_id`
- `review_m0_remote_consent.consumed_by_job_id -> review_m0_job.job_id`

元数据读取兼容 catalog/schema、大小写和 H2 MySQL-mode。迁移恢复逻辑仍可按既有名称识别，但 strict validate 不依赖名称。

主要新增回归：

- `strictValidationRejectsEveryMissingV002ForeignKey`：参数化逐个删除四类外键后均失败，共 4 个 discovered；
- `strictValidationUsesForeignKeyStructureRatherThanOnlyConstraintName`：同名但错误映射仍失败；
- `strictValidationRejectsCascadingRulesOnV002ForeignKeys`：错误级联删除规则失败；
- 原 `initializesAllFrozenTablesAndRepeatedInitializationIsIdempotent` 保持通过，证明完整 schema 与重复初始化正常。
