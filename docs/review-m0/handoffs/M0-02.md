### 2.3 Store、CAS、事务、owner 隔离与过期

状态：`IMPLEMENTED_AND_H2_VERIFIED`

- `ReviewCaseStore` / `JdbcReviewCaseStore`：Case 创建、owner-only 查询、快照读取、修订 CAS、正式清单快照发布。
- `ReviewReportStore` / `JdbcReviewReportStore`：owner-only 当前/历史报告查询和同一事务内结果发布。
- 所有对外 Case/报告/Job 查询均把稳定 `ownerId` 字符串作为 SQL 条件；异主读取返回不存在，没有管理员绕过入口。
- `basisRevision`、`checklistRevision`、`materialSetRevision`、`assignmentRevision`、`nameRevision`、引擎版本变化均有基础设施入口；当前报告在同一事务内变为 `OUTDATED` 并清空 Case 当前报告指针，已过期报告不能恢复为 CURRENT。
- 正式清单发布在同一事务内执行候选确认、旧正式版本 supersede、Case 指针/修订 CAS 和旧报告过期；basis 修订还把当前快照/正式清单标为 `STALE_BASIS`。
- 报告发布锁定 Job 与 Case，复核冻结输入修订/快照，在同一事务内写报告、finding、evidence、Case 当前报告和 Job 终态。
- `(case_id, input_fingerprint)` 唯一，保证一个 Case/输入指纹最多一个正式报告；同一 Job 和同一指纹重放返回原报告，过期报告不会被重新置为 CURRENT。
- 确定性 finding 必须同时拥有 RULE 与 MATERIAL 两侧证据；证据规范 JSON/摘要在存取边界校验。
- 修订写入与 OUTDATED 写入的原子回滚、CAS 竞争、同输入正式报告唯一性、owner 隔离均有专项测试。

### 2.4 幂等基础设施

状态：`IMPLEMENTED_AND_H2_VERIFIED`

- 幂等域固定为 `(ownerId, httpMethod, canonicalPath, idempotencyKey)`；载荷先生成规范 JSON，再以 SHA-256 作为 request digest。
- 同键同 digest：进行中返回稳定进行中状态，完成后重放原 response status/type/id 和原 Job。
- 同键不同 digest：抛出冻结 `REVIEW_M0_IDEMPOTENCY_CONFLICT`。
- 并发插入由数据库主键竞争收敛为一个创建者；失败事务回滚不会遗留半完成幂等行或重复 Job。
- `ReviewM0JobSubmissionService` 把幂等 claim、QUEUED Job 创建和 202/JOB/id 结果记录放在一个事务中。

### 2.5 Job、租约、checkpoint、恢复、取消与结果发布

状态：`IMPLEMENTED_AND_H2_VERIFIED`

- `ReviewM0JobHandler` 是按 `ReviewJobType` 注册的独立 SPI；`ReviewM0JobHandlerRegistry` 启动时拒绝同类型重复 handler。
- `JdbcReviewM0JobStore` 提供 QUEUED/过期 RUNNING 获取、租约 CAS、heartbeat、retry 释放、checkpoint、取消、失败和结果发布。
- 两 worker 竞争一个 Job 时只有一个持有租约；过期 RUNNING 可由新 worker 恢复并增加 attempt。
- checkpoint 以 `(job_id, checkpoint_key)` 唯一，规范 JSON/digest 相同重放无副作用，载荷不同稳定冲突。
- `CANCEL_REQUESTED` 不再被领取，也不能写新 checkpoint；QUEUED 可直接取消，RUNNING 由持有租约的 worker 收敛为 CANCELLED；CANCELLED 不发布结果。
- `ReviewM0JobDispatcher` 只做数据库轮询后的确定性 handler 派发；retryable 错误通过租约释放/重取推进，超过最大尝试后失败。没有内置具体 M0-03/M0-05 handler，也没有创建 scheduler 或外部队列消费者。
- 结果 publication callback 与 Job `SUCCEEDED` 同事务；发布前异常整体回滚，发布完成后的重放不再次调用 callback，覆盖发布前/后崩溃 fixture 的重复结果边界。
- `ReviewM0RemoteCallStore` 在实际 request digest 与已确认 consent payload digest 相同后原子写 `SEND_INTENT` 并消费授权；一个 Job 最多一条远程调用。`OUTCOME_UNKNOWN` 不会被当成可自动重发状态。

## 5. SPI、表与后续集成前置

### M0-03 可依赖

1. 领域入口：`OfficialBasis`、`OfficialBasisSourceLocator`、`ChecklistRevision`、`ChecklistRequirement`、`RequirementRevision`、`ChecklistSnapshot`、`RemotePreview`、`RemoteConsent`、`InputDiagnostic` 及冻结枚举/错误码。
2. 清单发布入口：`ReviewCaseStore.publishChecklistSnapshotOwned(...)`；它负责 Case CAS、正式版本唯一、旧版本 supersede、旧报告 OUTDATED 和指针更新。
3. basis/清单导致的过期入口：`ReviewCaseStore.advanceRevisionOwned(..., RevisionKind.BASIS, ...)` 或外层事务中的相应清单发布调用。
4. Job 入口：实现 `ReviewM0JobHandler` 并作为 Spring bean 注册；使用 `ReviewM0JobSubmissionService` 创建幂等 QUEUED Job，使用 `ReviewM0JobStore` 保存 checkpoint/终态。
5. 远程调用入口：只有预览确认后才能调用 `ReviewM0RemoteCallStore.beginSendIntent(...)`；实际 payload digest 必须等于 consent digest。
6. 表入口：`review_m0_official_basis`、`review_m0_checklist_revision`、`review_m0_requirement*`、`review_m0_checklist_snapshot`、`review_m0_remote_preview`、`review_m0_remote_consent`、`review_m0_input_diagnostic`。
7. M0-03 写自己的冻结表时必须由自己的应用服务开启外层 `REQUIRED` 事务，并在同一事务中调用本 Store 的修订/发布方法；内部 `TransactionTemplate` 会加入该事务。不得拆成“先写业务表、后标 OUTDATED”的两个事务。
