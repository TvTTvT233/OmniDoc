# Review M0：产品与范围冻结

## 1. 目标

Review M0 只回答两个问题：

1. 在用户已确认“本轮材料上传完毕”的前提下，正式清单要求的材料是否齐全；
2. 每个提交材料的逻辑 `submissionFileName` 是否符合正式清单和全局安全命名规则。

输出必须可追溯、可恢复、可重跑，并明确区分确定性问题、不能确认和系统失败。

## 2. 严格范围

### 2.1 M0 做

- 用户手动分类官方依据；
- 从官方依据提取候选材料清单；
- 用户确认、新增、改写、启用或停用候选项目；
- 将确认结果发布为不可变正式清单快照；
- 引用既有文件并建立非破坏性的逻辑 `submissionFileName`；
- 校验正式文件类型和 ZIP 容器结构；
- 在用户确认上传完毕后，按正式清单检查材料齐全性；
- 检查逻辑文件名；
- 输出规则证据、材料或材料集合证据；
- 保存忽略决定但不删除问题；
- 后台恢复、幂等、取消、单文件增量重审；
- 在输入变化时把旧报告标为 `OUTDATED`；
- 按逻辑文件名下载单份非破坏性副本。

### 2.2 M0 不做

- 错别字、语法、表达或内容润色；
- 表格或正文漏填、字段完整性、格式填写规范；
- 资格条件或获奖概率判断；
- 印章、签章真实性、是否已签章、签章日期判断；
- 跨材料事实一致性；
- 申报成果是否被证明材料支持；
- 对正文、表格、图片内容作补写、修改或覆盖；
- 自动提交材料；
- 把候选提取结果当作正式规则；
- 以模型推断材料存在、材料用途或用户意图；
- 另建文件存储、文档解析、RAG 或 Agent 基础设施。

只要一个发现依赖正文事实、资格解释、日期、签章、语义一致性或写作偏好，它就不属于 M0，不得以别的错误码绕回 M0。

## 3. 已确认的产品事实

以下事实来自本任务明确边界，可以作为验收依据：

1. M0 严格只做材料齐全性和文件命名。
2. 官方依据必须由用户手动分类上传。
3. 官方依据只产生候选清单；用户确认、新增、改写、停用后才能正式审查。
4. 来源谱系必须区分官方提取、用户新增和用户改写。
5. `submissionFileName` 是逻辑名称；不得修改原始文件名、文件内容或 MinIO `objectKey`。
6. 用户可以按 `submissionFileName` 下载单份副本。
7. 正式顶层格式只允许 PDF、DOCX、XLSX、JPG、PNG、ZIP。
8. ZIP 只作容器，禁止嵌套 ZIP，叶子条目只允许 PDF、DOCX、XLSX、JPG、PNG。
9. 用户未确认上传完毕前不得输出 `MISSING`。
10. 解析失败、加密、损坏或 OCR 不足必须表示为 `CANNOT_CONFIRM`。
11. 模型或系统错误不得表示为材料缺失。
12. 每个确定性结论必须同时有规则证据和材料/材料集合证据。
13. 忽略的问题必须保留，且当前报告包含忽略问题时不能为 `M0_READY`。
14. 默认本地保存；发送远程模型前必须展示可调整的脱敏预览并取得用户确认。
15. 后台任务必须可恢复、幂等、可取消，并支持单文件增量重审。
16. 清单或官方依据变化必须使旧报告 `OUTDATED`。

## 4. 官方依据与清单

### 4.1 官方依据分类

M0 冻结以下 `OfficialBasisRole`：

- `APPLICATION_NOTICE`：申报通知；
- `FILLING_GUIDE`：填写说明；
- `OFFICIAL_TEMPLATE`：官方模板。

分类动作必须来自当前案例所有者。系统可以建议分类，但建议不得代替用户手动确认；建议能力本身不属于 M0 必交付。

同一角色允许引用多个文件，以避免把“每类只能一个文件”擅自写成产品事实。文件顺序、冲突优先级和重复文件的 UI 处理见待确认事项；在未确认前，系统不得自动丢弃任一来源。

### 4.2 来源谱系

每个清单项目有稳定 `requirementId`，并记录完整修订链：

- `origin=OFFICIAL_EXTRACTED`：最初由官方依据提取；
- `origin=USER_ADDED`：最初由用户新增；
- `authorship=EXTRACTED_TEXT`：当前文字仍为提取版本；
- `authorship=USER_REWRITTEN`：当前文字已经用户改写。

用户改写官方提取项目时，`origin` 仍为 `OFFICIAL_EXTRACTED`，官方定位证据不得被删除；同时新增用户改写修订。用户停用项目只改变是否进入下一份正式快照，不删除项目和谱系。

### 4.3 候选到正式清单

正式清单发布前，每个启用项目必须由用户确认以下结构化字段：

- 展示名称；
- 是否适用于本案例；
- 最少需要的材料单元数量；
- 文件名规则；
- 来源谱系。

正式审查不读取候选草稿，不读取“模型最新输出”，只读取一个不可变 `checklistSnapshotId`。清单的新增、改写、启停或重新确认都会产生新修订；已经使用旧快照生成的报告保留但变为 `OUTDATED`。

对于用户新增或改写的规则，报告必须明确展示其用户修订谱系，不得把它伪装为官方原文。用户确认的正式清单项目本身可以成为规则证据；若保留官方定位，同时展示官方定位和用户改写关系。

## 5. 提交材料与逻辑文件名

### 5.1 非破坏性引用

Review M0 通过平台 `fileId` 引用既有文件。Review 数据库可以保存审计所需的元数据快照和内容摘要，但不得：

- 更新 `file_metadata.originalFileName`；
- 更新 `file_metadata.fileName` 来模拟逻辑改名；
- 移动、重写或替换原始 MinIO 对象；
- 更新原始 `objectKey`；
- 覆盖原始文件内容。

逻辑改名只更新 Review 自有材料记录的 `submissionFileName`，并增加提交材料修订号。

### 5.2 `submissionFileName`

`submissionFileName` 是一个叶子文件名，不是路径：

- 不允许 `/`、`\`、NUL、控制字符、绝对路径、`.` 或 `..`；
- 比较前采用 Unicode NFC；
- 扩展名比较不区分大小写；
- 扩展名必须与实际材料类型一致；
- 逻辑名的原始大小写和 Unicode 字符在下载时保留；
- 相同逻辑名的不同材料仍由 `materialId` 区分，下载 API 不以文件名作资源主键。

项目级 `EXACT/REGEX` 文件名规则必须由用户逐条确认 `caseSensitive=true|false`，系统不设隐藏的大小写默认；扩展名能否代表正式格式始终不区分大小写。`NONE` 的 `caseSensitive` 必须为 `null`。

单文件下载必须返回该材料单元的字节，`Content-Disposition` 使用其当前 `submissionFileName`。普通文件直接流式读取原文件；ZIP 叶子条目从原容器中安全流式读取单个条目。两者都不得为了下载而修改原文件或 `objectKey`。

### 5.3 正式格式

以下白名单同时适用于官方依据源和提交材料源。冻结 `FormalFileType`：

- `PDF`
- `DOCX`
- `XLSX`
- `JPG`
- `PNG`
- `ZIP`

扩展名映射固定为 `.pdf`、`.docx`、`.xlsx`、`.jpg`、`.png`、`.zip`，比较不区分大小写。`.doc`、`.xls`、`.jpeg` 及其他扩展不在 M0 正式白名单；不能仅凭 MIME 把它们改判为白名单格式。

类型不能只信任浏览器 MIME；必须结合扩展名和文件签名/可打开性校验。扩展名不在白名单的顶层文件不进入正式材料集，附加请求返回 `REVIEW_M0_UNSUPPORTED_FILE_TYPE`。白名单类型在深度校验时发现加密、损坏或类型不一致，保留引用并产生 `CANNOT_CONFIRM`，不能变成 `MISSING`。

ZIP 只作容器：

- ZIP 容器本身不是满足清单项目的材料单元，也不执行清单文件名规则；
- 每个合法叶子条目形成独立 `materialId` 和 `submissionFileName`；
- 官方依据 ZIP 的用户手动分类作用于容器内全部合法叶子；官方定位必须额外记录 `entryPath` 和条目摘要；
- 嵌套 ZIP、加密条目、损坏条目、路径穿越、重复规范化路径或非白名单叶子条目产生 `CANNOT_CONFIRM` 诊断；
- 目录条目忽略；
- ZIP 内条目的原始路径只作证据，不作为 `submissionFileName`；
- ZIP 安全上限必须有拒绝优先的技术配置，具体文件数、单项大小和展开比率属于待确认容量，不得写成产品承诺。

## 6. 材料分配与缺失判定

一个材料是否满足某个清单项目，必须有已确认的 `MaterialAssignment`。系统建议的分配只有在用户确认后才计入；M0 不根据正文语义猜测用途。

当且仅当以下条件全部成立，才能输出 `MISSING`：

1. 使用当前且已确认的正式清单快照；
2. 该项目启用且 `applicability=APPLIES`；
3. 用户对当前 `submissionRevision` 明确确认上传完毕；
4. 可用且已确认分配的材料数少于 `minimumCount`；
5. 当前提交材料集合不存在任何未决 `CANNOT_CONFIRM`；M0 不猜测一个不能处理的输入原本用于满足哪个项目；
6. 发现同时引用清单快照规则证据和本次上传确认覆盖的材料集合证据。

如果用户没有确认当前材料修订上传完毕，正式审查请求直接拒绝，不生成 `MISSING` 报告。如果当前集合中任一输入因解析、加密、损坏或 OCR 不足无法判断，输出 `CANNOT_CONFIRM`；在全部未决诊断解决或对应源被用户移除前，本次报告不输出任何 `MISSING`。这是不猜测材料用途的保守边界。

## 7. `CANNOT_CONFIRM` 与系统失败

`CANNOT_CONFIRM` 是可审计的业务诊断/审查结果，表示输入确实存在但不能可靠处理。它可以在正式报告之前附着于官方依据或材料，也可以进入正式报告。冻结原因包括：

- `PARSE_FAILED`
- `ENCRYPTED`
- `CORRUPTED`
- `OCR_INSUFFICIENT`
- `TYPE_MISMATCH`
- `NESTED_ARCHIVE_NOT_ALLOWED`
- `ARCHIVE_ENTRY_UNSUPPORTED`
- `ARCHIVE_SAFETY_LIMIT_EXCEEDED`
- `SOURCE_FILE_UNAVAILABLE`

OCR 只可能用于官方依据候选提取。M0 不读取提交材料正文，因此不能因为提交图片的文字少或 OCR 低置信度而扩大为正文审查；如果官方依据必须经 OCR 才能提取清单且质量不足，则记录 `OCR_INSUFFICIENT`。

模型超时、模型鉴权失败、数据库不可用、队列异常、未知异常等属于任务 `FAILED` 和 API 错误，不属于 `CANNOT_CONFIRM`，更不属于 `MISSING`。失败任务不得发布半成品正式清单或当前报告。

## 8. 本地保存与远程模型

- 新案例默认 `processingMode=LOCAL_ONLY`。
- 正式 M0 齐全性/命名审查是确定性处理，不需要远程模型。
- 官方依据候选提取若选择远程模型，必须先生成发送载荷的脱敏预览。
- 用户可以编辑预览；任何编辑都会产生新 `payloadDigest` 并使旧确认失效。
- 用户确认必须绑定案例、操作、输入修订、完整预览摘要和 `payloadDigest`。
- 一个确认只授权一个逻辑后台任务；同一任务的幂等恢复可以重用，不能授权新任务或不同载荷。
- 发送内容必须与最后确认的预览字节等价；不得在发送时重新加入被删字段或原文。
- 远程模型响应只产生候选和诊断，永远不能自动发布正式清单。
- 原始材料、预览、确认、响应和审计记录默认保存在 OmniDoc 部署边界内；远程发送是逐次显式例外。

具体远程供应商、模型、保留策略和默认脱敏类别未由用户确认，见下一节。

## 9. 待确认的产品事实

以下内容没有在本任务中得到用户确认。实现可以保留字段或配置位，但不得擅自把某个选项写成已确认产品行为：

| 编号 | 待确认事项 | 确认前约束 |
| --- | --- | --- |
| `P-01` | 案例、报告、预览和审计记录的保留期与用户删除能力 | 不自动物理删除；只实现契约要求的非破坏性保留 |
| `P-02` | 单文件大小、文件总数、ZIP 条目数、展开大小与压缩比的产品上限 | 使用可配置安全硬上限；不得宣传具体容量 |
| `P-03` | `submissionFileName` 的产品长度上限和重名 UX | API 保持明确错误；安全边界可配置，文件名不是资源主键；规则大小写由用户逐项确认 |
| `P-04` | 多份同类官方依据的显示顺序、冲突优先级和去重交互 | 全部保留并展示谱系，不自动选择权威版本 |
| `P-05` | 条件材料的业务问答与默认适用性 | 具条件的项目必须由用户明确选 `APPLIES` 或 `DOES_NOT_APPLY`；未决时为 `NEEDS_USER_DECISION` |
| `P-06` | 自动材料分配建议及其 UI | 只有用户确认的分配计数；建议不计数 |
| `P-07` | 忽略理由是否必填、是否允许撤销忽略 | 冻结最小能力为可选理由的 `IGNORE`；不得删除发现；确认前不提供撤销操作 |
| `P-08` | 远程供应商、模型、地区、服务端保留政策和默认脱敏字段 | 默认 `LOCAL_ONLY`，未确认不得配置产品默认远程发送 |
| `P-09` | Review M0 页面入口、路由、导航名称和通知方式 | 后端资源契约可实现；前端集成由后续产品确认和集成任务处理 |
| `P-10` | 中文展示文案、错误文案及国际化 | 机器码冻结；展示文案不作为 API 稳定字段 |
| `P-11` | 用户能否把同一材料确认分配给多个清单项目 | 存储/API 支持多对多；是否在 UI 限制须待确认 |
| `P-12` | 清单项目除最小数量外的“恰好 N 个”“任选 N 个”等组合规则 | M0 首版只冻结 `minimumCount`；复杂组合规则需新的产品确认和契约版本 |
| `P-13` | 已创建案例是否允许切换本地/远程处理模式 | 确认前模式创建后不可变；需要不同模式时新建案例 |

待确认项不阻止实现已经冻结的保守路径，但不能通过隐藏默认值改变用户结果。
