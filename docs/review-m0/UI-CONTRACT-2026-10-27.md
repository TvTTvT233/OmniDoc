# Review M0 页面集成契约增补

本增补基于用户2026-10-27授权“列出开发方案然后进行Review M0收尾与前端接入”，及其明确选择“先完成手工确认规则的完整流程，自动提取单独下一步开发”。保留REVIEW_M0_CONTRACT_V1已有资源字段和规则，不改变正式审查真值表。

## 页面范围

- `/review-m0`：当前登录用户案例列表及创建；导航名“材料预审”。
- `/review-m0/:caseId`：官方依据、手工确认清单、材料/分配、报告与任务。
- 创建明确传LOCAL_ONLY；不提供远程模式入口，不调用外部模型。
- 用户新增规则标记USER_ADDED；未实现的官方自动抽取明确显示未接入，不伪造OFFICIAL_EXTRACTED来源。
- 多对多材料分配采用逐项显式确认；不按内容猜用途。
- 仅IGNORE、可选理由，保留问题及证据，不提供未冻结的撤销。
- 官方依据使用原文件与摘要，Review证据不冒用document-service版本引用ID。
- 本轮手工流程不要求附加官方依据。未处理ATTACHED依据按原契约阻止正式清单发布，页面必须说明这一限制并提供移除案例引用（原文件保留）的操作，不能引导用户进入无法完成的必经上传流程。

## 新增只读案例列表

`GET /api/review-m0/cases?limit=20&cursor=<opaque>`

用于服务端持久案例发现和跨页面/刷新恢复，不能用浏览器本地案例记录替代。

- 身份仅取认证上下文，只返回当前owner的案例。
- `limit`默认20，合法范围1～100。
- `cursor`省略从首页读取；续页只能使用服务端返回的规范不透明值。
- 稳定排序`createdAt DESC, caseId DESC`，keyset分页，不使用易变化的updatedAt作为排序游标。
- cursor须指向当前owner存在的案例；非规范、异owner、不存在的cursor或越界limit均HTTP400 `REVIEW_M0_REQUEST_INVALID`，未登录沿用Review结构化401。
- 成功HTTP200裸资源：`{ "items": [CaseResponse], "nextCursor": null或string }`。CaseResponse保持既有创建/详情响应字段。空列表items=[]、nextCursor=null。
- 不接受userId作为授权输入；游标内容不能授予资源权限。
- 不新增案例删除、模式切换或保留期语义。

## 预审可用文件上传与列表（2026-10-29）

浏览器联调确认旧 `/api/files/upload` 和 `/api/files/list` 不提供预审要求的 owner-aware 事实，不能直接作为本页材料来源。预审页面改用既有 `POST /api/files/owned` 上传，并新增只读列表：

`GET /api/files/owned?page=1&size=20`

- 身份仅取当前 JWT，查询限定该 owner 且 ACTIVE；不接受 ownerId/userId 查询参数切换身份。
- page 默认 1，范围 1～10000；size 默认 20，范围 1～100。非法范围、非数字返回 400，未认证返回 401。
- 按 `create_time DESC, file_id DESC` 稳定排序，裸响应 `{ "items": [OwnedFileMetadataDTO], "hasMore": boolean }`。不返回内部对象定位信息或总数。
- 使用 offset 分页；新上传后重新加载第一页。选择结果和刷新均来自服务端，不将页面内存缓存伪装为文件库。
- 旧数据没有可信 owner 的文件不列入预审可用列表；本轮不推断或回填原文件归属，也不修改旧文件模块。
- 选择上传文件仍须用户明确加入当前案例；移除案例引用不删除原件。

## 写入和错误处理

沿用所有写请求Idempotency-Key、PATCH/版本敏感动作expectedVersion要求。同一次未知网络结果重试须保持原键与载荷；用户主动编辑后新建操作键。冲突不自动覆盖。读取页面状态以服务端为准，刷新不重新提交审查、不重复创建资源。

`GET /cases/{caseId}/checklist-draft`读取该案例最新清单修订并保留其lifecycle，允许返回已发布修订用于页面查看和继续编辑，不能因最新已发布而倒退到更旧草稿。发布操作仍只能使用最新`CANDIDATE_DRAFT`及其匹配修订和用户逐项确认；已发布项目的编辑创建新草稿，不复活旧候选。

历史报告使用其自身`checklistSnapshotId`读取规则；显式打开历史报告时不能被当前报告或无关已完成任务覆盖。主动提交新任务后才跟踪新任务的完成结果，用户也可明确切换查看最新报告。

前端应明确区分“未确认规则”“未确认本轮材料上传完毕”“任务失败”“不能确认”“报告已过期”和“当前报告”。缺少成功响应时禁止本地构造成功结果；用户未确认上传完毕前不能呈现材料缺失结论。

## 后台材料重新核验的内部认证增补

真实后台审查必须重新核验源材料，不能仅凭上传时缓存判断仍可用。既有用户JWT委派依赖当前HTTP请求，后台worker没有该上下文。补充file-service的`/internal/review-files`只读窄接口，由独立服务凭据认证，AI后台发送任务记录中的可信owner和fileId；文件服务逐次复用owner-aware读取和原件完整性核验。具体路由及header在后端实现报告列明。

- 服务凭据无弱默认、不进入Git、请求日志、任务表或浏览器；未配置或认证失败显式拒绝。
- 内部通道不暴露在网关，不接受用户JWT替代服务认证，不支持写入/删除/改名。
- owner只来自服务端已授权任务，不信任前端传入的owner字段；文件不存在/不属于该owner统一拒绝。
- 普通同步用户请求继续使用原JWT委派，后台不保存或长期重用用户Bearer。
- 必须验证未认证、伪造用户header/JWT、错误服务凭据、异owner、合法后台读、文件不可用以及原件不变。
