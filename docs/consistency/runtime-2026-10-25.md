## 结论与边界

本轮无外部模型的运行验收通过：真实文档保存、索引 worker、权限、当前检索闸门、持久会话历史引用、删除拒绝访问及故障恢复链路均取得证据。可靠性矩阵 **26/26 通过**。浏览器使用实际 Edge、Vite 和 HTTP，没有拦截或伪造接口响应，五个阶段均通过。

成功索引使用仅位于测试 classpath 的 `SyntheticConsistencyApplication`，提供确定性 16 维 Embedding 和明确标记的合成回答；其余 worker、内部 HTTP、MySQL、Redis DB11、baseline VectorStore 均为真实实现。生产 JAR 不包含合成类。全部成功发布由真实 worker 完成；只有迟到拒绝测试对真实已退役租约发送空分段 complete 负向探针，返回 accepted=false/published=false。

这证明一致性机制和集成行为，不证明真实大模型回答质量、语义召回效果、外部 Tavily 或生产规模性能。真实 Qdrant 集成的三个自动测试仍属先前明确跳过项，本轮运行使用 baseline VectorStore。

## 环境和恢复

使用独立 Docker Compose 项目 `omnidoc-baseline-20261014` 的 MySQL、Redis、RabbitMQ、MinIO、Qdrant 容器；Java 17，五个应用端口 8080—8084。本轮只使用 Redis DB11 的合成索引，不刷新其他数据库。

10-26 续接时应用进程已不存在，Docker Desktop 停留在历史 `docker-offload.exe` 残留进程错误页，engine 探测挂起。核实历史 PID 已不存在后，正常 shutdown 请求有界超时，按实际进程路径停止卡住的 Desktop/backend 进程并隐藏重启。engine 恢复返回 29.3.1，随后启动原项目容器；没有 reset、prune、删除卷或触碰其他项目。

恢复后先以暂停 worker 模式启动，重新通过真实 HTTP 检查原 V1 READY、Redis 分段和数据库精确引用 **3/3**，并非仅根据数据库状态推断索引存在。原文档、generation、引用和持久会话均未重建。

## 故障与恢复矩阵

命令：`Test-WorkerReliability.ps1 -JavaPath <Java17> -DependencyClasspathFile .local/consistency-evidence/ai-test-classpath.txt`。结果文件：`worker-reliability-20261026-143006.json`，**26 个断言全部通过**。

1. 合成 Embedding 第二次调用受控失败，形成部分构建；真实 worker 第二 attempt 发布 V2，失败 generation 的 CLEANUP 成功。
2. V3 BUILDING 时公开保存 V4，旧 active 立即失效；最终只发布 V4，V3 注册引用数为零；真实旧租约迟到 complete 被拒绝。
3. V5 BUILDING 时停止已验证身份的 AI 进程，重新启动后等待自然租约超时；第二 attempt 以新 generation 发布，无手工改数据库时间或状态。
4. AI 普通 Disabled 模式保存 V6，失败且没有旧索引回退；恢复合成服务后公开 retry 返回202，配置 hash 保持不变并成功发布 V6。
5. 暂停 worker，通过公开 restore 恢复历史 V2，生成新的 V7，原始正文与 V2 相同，旧 active 即时清空；真实 worker 随后发布 V7。
6. 最终删除前，核实属于该测试 doc/V7 的单个 DB11 manifest 并私有备份。暂停 worker、删除文档后，仅将该键替换为无效 JSON。真实 CLEANUP 记录 INDEX_STORAGE_UNAVAILABLE；`finally` 还原 manifest 后第二 attempt 成功，pendingCleanup=0；V7 manifest、全部三段向量及元数据键实际不存在。

第六项是有明确作用域的坏数据故障注入，不代表观察到了生产故障，也不等同于 Redis 全体宕机容灾测试。备份保留在 `cleanup-manifest-backup.private.json`。全程没有整体暂停 Redis 或删除用户内容。
